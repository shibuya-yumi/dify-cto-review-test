# GitHub PR自動化の方法比較

## 🎯 **目的**
PRに`cto-review`ラベルが付いたら、`outline.md`をCTOの視点でレビューして自動コメントする

## 📋 **実現方法の比較**

### **方法1: Webhook Server（現在の方針）**

#### **仕組み**
```
GitHub PR (ラベル付与)
    ↓ HTTP POST (Webhook)
AlmaLinux VM (Webhookサーバー)
    ↓ API呼び出し
Dify API
    ↓ レスポンス
AlmaLinux VM
    ↓ コメント投稿
GitHub PR
```

#### **メリット・デメリット**
- ✅ **リアルタイム**: ラベル付与と同時に実行
- ✅ **スケーラブル**: 複数のリポジトリで利用可能
- ✅ **他の人も使える**: 誰でもラベル付与で実行
- ✅ **完全自動**: 人の介入不要
- ❌ **サーバー管理**: 24時間稼働が必要
- ❌ **ネットワーク設定**: 外部からのアクセス許可が必要

---

### **方法2: GitHub Actions（IPブロック問題あり）**

#### **仕組み**
```
GitHub PR (ラベル付与)
    ↓ 内部トリガー
GitHub Actions Runner
    ↓ スクリプト実行
Dify API（❌ IPブロック）
```

#### **メリット・デメリット**
- ✅ **設定簡単**: `.github/workflows/`に設定ファイル
- ✅ **メンテナンス不要**: GitHub管理
- ✅ **無料**: GitHub Actions無料枠
- ❌ **IPブロック**: DifyがGitHub ActionsのIPをブロック
- ❌ **解決困難**: WAFレベルでのブロック

---

### **方法3: Scheduled Polling（定期実行）**

#### **仕組み**
```
Cron Job (定期実行)
    ↓ GitHub API
未処理のPRをチェック
    ↓ 条件に合致する場合
Dify API呼び出し
    ↓ コメント投稿
GitHub PR
```

#### **実装例**
```bash
# crontab設定（5分毎に実行）
*/5 * * * * /opt/webhook-server/scripts/check-prs.sh

# check-prs.sh の概要
1. GitHub APIで最新のPRを取得
2. cto-reviewラベルが付いているPRを検索
3. まだ処理していないPRを特定
4. outline.mdレビューを実行
5. 処理済みマークを付与
```

#### **メリット・デメリット**
- ✅ **シンプル**: Webhookサーバー不要
- ✅ **安定**: 外部からのアクセス不要
- ✅ **デバッグ容易**: ローカルでテスト可能
- ✅ **権限問題なし**: 内部からの通信のみ
- ❌ **遅延**: 最大5分程度の遅延
- ❌ **重複実行リスク**: 同時実行の制御が必要
- ❌ **状態管理**: 処理済み管理が複雑

---

### **方法4: Manual Script（手動実行）**

#### **仕組み**
```
開発者が手動実行
    ↓ スクリプト実行
特定のPRを指定
    ↓ Dify API
レビュー生成
    ↓ 手動またはスクリプトで投稿
GitHub PR
```

#### **実装例**
```bash
# 使用方法
./scripts/review-pr.sh owner/repo 123

# 処理内容
1. 指定されたPR番号のoutline.mdを取得
2. Dify APIでレビュー生成
3. PRにコメント投稿
```

#### **メリット・デメリット**
- ✅ **最もシンプル**: 既存のローカルスクリプト活用
- ✅ **確実**: 実行タイミングを制御可能
- ✅ **デバッグ容易**: 問題があればすぐ確認
- ✅ **サーバー不要**: インフラ管理不要
- ❌ **手動**: 人の介入が必要
- ❌ **スケールしない**: 大量のPRに対応困難
- ❌ **忘れやすい**: ラベル付与を忘れる可能性

---

### **方法5: GitHub App**

#### **仕組み**
```
GitHub App (インストール型)
    ↓ Webhook受信
AlmaLinux VM
    ↓ OAuth認証
GitHub API
    ↓ Dify API
レビュー生成・投稿
```

#### **メリット・デメリット**
- ✅ **プロフェッショナル**: 企業レベルの実装
- ✅ **権限管理**: 細かい権限制御
- ✅ **複数組織**: 他の組織でも利用可能
- ✅ **マーケットプレイス**: GitHub Marketplaceで公開可能
- ❌ **複雑**: OAuth、JWT等の実装が必要
- ❌ **審査**: GitHub App登録に審査が必要
- ❌ **開発時間**: 実装に時間がかかる

---

### **方法6: Browser Extension**

#### **仕組み**
```
ブラウザ拡張機能
    ↓ GitHub画面で動作
ボタンクリック
    ↓ バックグラウンドで実行
Dify API
    ↓ 結果表示
GitHub画面に挿入
```

#### **メリット・デメリット**
- ✅ **ユーザーフレンドリー**: GitHubの画面に統合
- ✅ **インストール簡単**: Chrome拡張として配布
- ✅ **サーバー不要**: クライアントサイドで完結
- ❌ **ブラウザ依存**: Chrome等の特定ブラウザ必要
- ❌ **CORS問題**: APIアクセスに制限
- ❌ **配布**: 各ユーザーがインストール必要

## 🎯 **AlmaLinux環境での推奨**

### **第1候補: Webhook Server**
- リアルタイム性と自動化のバランスが最適
- AlmaLinux環境を最大活用
- 他の人も簡単に利用可能

### **第2候補: Scheduled Polling**
- Webhookが困難な場合の代替案
- よりシンプルで安定
- ネットワーク設定が簡単

### **第3候補: Manual Script**
- 最初のプロトタイプとして
- 動作確認後にWebhook化

## 🚀 **実装ステップの提案**

### **段階1: Manual Script**
```bash
# AlmaLinux環境で動作確認
./scripts/review-pr.sh owner/repo 123
```

### **段階2: Scheduled Polling**
```bash
# 定期実行で自動化
crontab -e
*/5 * * * * /opt/scripts/check-prs.sh
```

### **段階3: Webhook Server**
```bash
# リアルタイム化
systemctl start webhook-server
```
